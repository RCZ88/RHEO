# DevTrigger Panel — Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** A dev-only modal in the running app that can fire, inject data into, and schedule every auto-trigger popup/behavior without waiting for real conditions, plus a live armed-state snapshot.

**Architecture:** Single `DevTriggerPanel` component rendered at the app root in `App.tsx` (like the other global modals at `src/App.tsx:3005–3390`). All fire/inject/schedule handlers live in `App.tsx` next to the states they control. No new IPC, no new backend — reuses existing handlers: `checkSleepDetection`, `confirmSleep`, `computeAdjacentGaps`, `detectUsageGaps`, `getExternalActivities`, `getExternalSessions`, `loadAfkQueue`/`saveAfkQueue`, `setPreference`.

**Tech Stack:** React 18 + TypeScript + Tailwind (existing project conventions), framer-motion for the panel open/close, lucide-react icons.

**Build:** `node agent/docs/feature-docs/deskflow-multi-agent-coordination/agent-coordination/run-exclusive.mjs build --forbid app -- npm run build`

**Verification:** Build passes + manual click-through of every control (no test runner in this repo — MEMORY 08-04).

---

## Current Context / Assumptions

- The app already has 14+ auto-trigger popups/behaviors driven by React state + IPC + visibility/focus/idle listeners in `src/App.tsx`.
- All the React state for these popups already lives in `App.tsx` at module scope (not in separate pages), so a single root-level panel can control all of them.
- There is no existing dev/debug surface for these — the only way to exercise them today is to wait for real conditions or click hidden UI.
- Coordination wrapper exists at `agent/docs/feature-docs/deskflow-multi-agent-coordination/agent-coordination/run-exclusive.mjs`.

**Out of scope for v1 (deferred):**
- Saved schedule presets
- Main-process/timer-heartbeat manipulation
- New IPC endpoints
- Unit tests (none configured — MEMORY 08-04)

### Task 4: Build the "Schedule + State" tab

**Files:**

**Step 4a: Schedule state + handlers**

In `App.tsx`:

```ts
interface ScheduledFire {
  id: number;
  label: string;
  target: string; // popup id matching TriggerRow.id
  delaySeconds: number;
  prep: boolean; // whether to run prep first
  createdAt: number;
  cancelled: boolean;
}
const [scheduledFires, setScheduledFires] = useState<ScheduledFire[]>([]);
const scheduleIdCounter = useRef(1);
```

Handler `scheduleFire(targetId, label, delaySeconds, prep)`:
- Creates a `ScheduledFire` entry with `createdAt: Date.now()`
- Starts a `setTimeout` that, when fired, checks `!entry.cancelled` then calls the target's `prepAndFire` (if prep) or `fire`; removes the timeout on cancel
- Stores the timeout handle in a ref map `scheduleTimeoutRef.current[id] = setTimeout(...)` so cancel can clear it

Handler `cancelScheduledFire(id)`:
- Sets `cancelled: true` on the entry
- Clears the timeout from the ref map
- Removes the entry from the list

Handler `clearAllScheduled()` — cancels all.

The schedule form (in-panel): target select (populate from the same registry as the Fire tab), label text input, delay seconds number, Prep checkbox, Schedule button. Below it: the list of scheduled entries with cancel buttons + time-until-fire countdown (updates every second via `setInterval` while the panel is open).

**Step 4b: Armed-state snapshot**

In `App.tsx`, the snapshot is just reading current state — pass it as props. The snapshot object:

Expose `pendingIdleRangeRef.current` by reading it in the snapshot function (refs are readable in render).

## Risks, Tradeoffs, Open Questions

- **Ref reading in render:** `pendingIdleRangeRef.current` and friends are readable during render, but if they're mutated outside React's render cycle the snapshot may be one tick stale — acceptable for a dev tool.
- **Banner override:** the banner condition change at line 2570 must not break the real banner path when `devForceGapBannerMinutes` is null — test both paths.
- **TutorialOverlay:** if it's always-mounted with no open state, the Fire row for it should be marked "always on" rather than a button that does nothing — inspect the component first.
- **PairPhoneModal data shape:** confirm the exact shape expected by `PairPhoneModal` (line 3385) before hardcoding the test entry — read that component's props.
- **Detach behavior:** the panel stays mounted at root and `open` prop controls visibility; "detach" means don't auto-close on navigation — but the existing top-bar is already route-conditional (line 2583: `location.pathname !== '/terminal' && !solarOverlayActive`). Decide whether the detach toggle also bypasses the top-bar hide — recommend: yes, so the panel is reachable on every route when detached.
- **Release gating:** `DEV_TRIGGER_ENABLED` const at the top of App.tsx gates the button + the panel render, so a release build can set it false and ship zero dev surface without deleting code.
