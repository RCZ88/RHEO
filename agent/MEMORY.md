- [2026-10-05] A BENIGN BROWSER WARNING BECOMES A FATAL SCREEN KILL BECAUSE EVERY `window.onerror` IS ROUTED TO THE REACT ERROR BOUNDARY — AND THE FIX PACKET'S NAMED ROOT CAUSE WAS THE *WARNING SOURCE*, NOT THE CRASH. `src/main.tsx` did `window.addEventListener('error', e => routeToBoundary(e.error || e.message))`, and Chromium delivers `ResizeObserver loop completed with undelivered notifications` as a window error with `error === null` and a string message. So any layout hiccup anywhere in the app unmounted the whole screen. The same handler also escalated RESOURCE-LOAD failures: a failed `<img>`/`<script>` arrives with an empty `error` AND an empty `message`, so `routeToBoundary('')` tripped the boundary with a *blank* error message. **RULE: an error boundary must never be reachable by a browser-emitted warning. Filter at the choke point (`isBenignBrowserError`: null/undefined, empty string, `resizeobserver loop`, `script error.`) AND at the listener (`e.target !== window` = resource load, not a render error).** **THE BIGGER LESSON — a FIX PACKET'S ROOT CAUSE IS A HYPOTHESIS, NOT A FINDING.** The packet attributed 'every lesson crashes' to the ZoomPan ResizeObserver loop and said the cycle 'never terminates'. I wrote a numeric probe of the real geometry and the fit math reached a fixed point in 2 passes — the loop is NOT provably unbounded, because `el.style.height` is derived from `cw/nw` (self-consistent) and `scrollWidth` is layout-based, so `transform: scale` does not feed back into the measurement. I hardened ZoomPan anyway (idempotent-fit early return + stop observing the mutated element — both cheap and correct), but the ACTUAL crash was one file away and the packet never mentioned it: **`ReaderView.tsx` returned `null` before its first `useEffect`, so it registered 0 hooks on the first render and ~20 on every render after — a conditional-hook-order violation, plus a render-phase `onSelectNode()` that updated the parent mid-render.** **RULE: when a packet says 'X causes Y', still check whether an early `return` sits above a hook list — and `return null` before hooks is a hook-count violation even when that branch only fires on the first render. Also: an early return that auto-selects state is usually an EFFECT that got written in the render phase.**

- [2026-10-05] A `catch { console.error() }` AROUND A PER-ROW SQL WRITE, FOLLOWED BY `return {applied, cursor}`, IS SILENT DATA LOSS — AND IT WAS THE ONLY REASON SYNC NEVER WORKED. Two independent defects sat on the same line of `sync-server/src/routes/sync.ts` and together explained two years of "the phone doesn't sync": `ON CONFLICT${target}` (no space) interpolated to `ON CONFLICTid`, AND the non-composite target was `"id"` where SQLite requires the PARENTHESISED `ON CONFLICT (id)`. So **every push that touched an existing row died with a SQLITE_ERROR** — while the handler still returned HTTP 200 `{applied:0, cursor}`. The desktop then advanced its cursor past rows that were never stored, so the data was unrecoverable AND the UI reported success. I only found it because I had just made failures return 500; the new error path tripped immediately on the first test push. **THE GENERAL RULE: an `ON CONFLICT` clause is built by string interpolation, so it is a silent-typo magnet — never eyeball it. The deeper rule is that a swallowed row error plus a success status is strictly worse than a crash: it converts a loud failure into a slow, permanent, invisible one. ANY loop over rows that writes must either roll up failures into the RESPONSE or fail the request — and "I logged it" is not a defence.** Same file, three more of the family: a cursor written as `maxTs || Date.now()` (MILLISECONDS) where every other cursor was seconds, and `datetime(<ms>,'unixepoch')` returns NULL rather than erroring — so pull was dead *permanently* for 57 of 59 users with no symptom beyond "no data"; `terminal_messages.updated_at` was never written so all 100 stored messages sat outside pull's filter; and `LIMIT 500` with no `ORDER BY`. **Corollary for aggregates: the server `SUM()`s `deskflow_foreground_sec` per day, so the client must send the DELTA since the last accepted push — sending a cumulative counter into a SUM over-counts quadratically (5 pushes of 60s store 300s, not 60s). Ask what the CONSUMER does with the column before choosing what the producer sends.**

- [2026-10-06] AN ALWAYS-ON-TOP OVERLAY MUST KEEP ITS HOVER REGION AND ITS CLICK REGION AS TWO SEPARATE RECTANGLES — AND CSS `pointer-events` IS NOT ENOUGH TO SEPARATE THEM. The Halo island reported "the hitbox interferes with my clicks", and the hitbox was innocent. `main.ts` shaped the click region from `geometry.expandedSize`, which is `{ width: calibration.expandedWidth, height: calibration.expandedHeight || MAX_CANVAS_HEIGHT }` — and `expandedHeight` is 0 unless a caller sets it, so `|| MAX_CANVAS_HEIGHT` silently substituted the CONTAINER for the content and the region became the whole 460x300 canvas. So the user widened the hover zone and the island ate clicks across the entire transparent window. **THREE RULES.** (1) **A HOVER ZONE AND A CLICK REGION ARE DIFFERENT RECTS BY CONSTRUCTION.** Derive both from one shared `computeSurfaceRect` so they cannot drift; a single rectangle used for both is the bug. Collapsed = `setIgnoreMouseEvents(true,{forward:true})` (cursor still reaches the app below; the island learns about it by POLLING `getCursorScreenPoint`). Expanded = `setIgnoreMouseEvents(false)` PLUS `win.setShape([surfaceRect])` — an X11/Win32 SHAPE, so the compositor routes a click to the window only inside the painted pixels. That is the difference between "usually does not interfere" and "cannot". `pointer-events:none` on the root is correct and necessary (HALO §12) but is NOT sufficient once the OS has delivered the event to an always-on-top window. (2) **A PROBE THAT PRINTS NUMBERS FOUND WHAT FOUR STATIC CHECKS COULD NOT.** esbuild, tsc and `validate:pages` were all clean; asserting `clickRegion === painted surface` for padY=0/120/240 printed `460x300` and named the field. Corollary, generalisable: **a size field defaulted with `a || FALLBACK` silently becomes the FALLBACK**, and the fallback here was a container rather than a content box — so prefer an explicit `??` with a numeric default, or assert the derived value. (3) **BEFORE ADDING USER CONTROLS, FIND OUT WHETHER STORED VALUES ARE EVER READ.** Every Halo setting wrote to the DB and did nothing: `halo:prefs` was sent from exactly one place (`did-finish-load`), and `toggleHaloIsland` only flipped the pin flag despite Settings promising "applies immediately via ⌘⇧H". **A stored-but-never-read preference is indistinguishable from a working one until runtime**, so the first question for any "make X customizable" task is `grep -rn '<channel>' src/` and count the send sites. Related: `onClick={() => setPinned(p => !p)}` on a surface whose state the MAIN process owns is the same bug in miniature — local React truth, remote authority, and the next poll tick overwrites it.

- [2026-10-06] A TRIGGER RECT DERIVED ONCE FOR ONE PHASE SILENTLY UNDER-COVERS THE OTHER, AND THE SYMPTOM IS AN OVERLAY THAT CLOSES UNDER THE CURSOR. The Halo FSM tested ONE rect forever: `computeGeometry` baked `hotZone` from `compactSize` only, so the island opened correctly on its 232x40 pill and then — the moment the cursor moved down onto the 460x236 expanded panel, the most natural thing to do after opening it — `inside` flipped false, the close timer ran, and it shut itself. A numeric probe put it at 4 of 6 cursor positions ON the island's own painted surface reporting `outside`. THE RULE: `inside` must be true for EVERY pixel the user can SEE, in EVERY phase. Keep ONE rect per phase (`hotZone` compact, `hotZoneExpanded` = union) and SELECT ON PHASE at the poll, because the union of all phases' rects is monotonically larger than any one of them and therefore cannot under-cover during the open/close animation. THREE COROLLARIES. (1) A `diag()` trail that logs one rect is what made this invisible — the log read a correct-looking 232x40 while the FSM was really testing it against a 460x236 panel; log BOTH, always. (2) Selecting a state-dependent value needs `(cond ? a : undefined) ?? fallback` — a bare `cond ? a : b` where `a` is a newly added field throws on every older geometry object. (3) When a probe assertion fails, check whether the EXPECTATION is wrong before touching the code: `unionRect` was correct and my hand-computed `45` should have been `40`; asserting the PROPERTY (all 8 corners contained + edges hug the inputs) instead of my arithmetic is what stops a probe from inventing a bug.

- [2026-10-01] EMBEDDING A BROWSER IS A THREE-PART JOB, AND THE PART THAT ACTUALLY BITES IS THE RECT SYNC. Electron's `WebContentsView` is a NATIVE view layered over the window — it is not an iframe, so a renderer component cannot contain it. The renderer only reserves an empty element and ships its `getBoundingClientRect()` to main on open/resize/scroll (ResizeObserver); if that rect drifts the native view floats over the wrong UI and reads to the user as a BLACK PANEL. Two further non-obvious requirements: use a `persist:` partition or Google sign-in is forgotten on every restart, and Google refuses OAuth from a webview whose UA contains "Electron", so `session.setUserAgent(<real Chrome UA>)` plus `--user-agent=` in `webPreferences.additionalArguments` is what makes sign-in work. Security that is not optional because the panel renders untrusted remote pages: `nodeIntegration:false`, `contextIsolation:true`, `sandbox:true`, `setWindowOpenHandler` → `shell.openExternal` + deny, and refuse any navigation that is not http/https. And keep an external-browser escape hatch: some sites refuse an embedded session, and a panel that cannot be opened must never be a dead end.
