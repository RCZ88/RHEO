- [2026-10-16] **RHEO HAS TWO TRACKING WRITERS AND ONLY ONE EXCLUDES SLEEP — SO A SUSPEND BECOMES FABRICATED USAGE IN HALF THE CASES.** WRITER A (`src/main.ts` ~6363, the Electron app) is CORRECT: it ends the session at `lastSuccessfulObservationTime - sessionStart`, so unobservable suspend time is never logged. Spec + recon: `agent/docs/generate-prompt-docs/tracking-time-adjustment-16102026/`. **UPDATE (same day): WRITER B IS NOW FIXED** — `feed()`/`flush()` were given separate ATTEMPT and SUCCESS clocks with `flush(reason, endedAtMs)` clamped to `lastSuccessfulObservationMs`, and `tick()` now reports `{ok:false}` instead of swallowing failures. - [2026-10-16] **THE "139-HOUR DAY" WAS NOT SLEEP AT ALL — IT WAS BROWSER WRITE AMPLIFICATION FROM CONFLATING TWO EXTENSION PAYLOAD SHAPES, AND A `let` IN THE TEMPORAL DEAD ZONE.** The extension sends TWO shapes and they do not mean the same thing: **periodic** (`is_periodic:true, delta_ms>0`) has `timestamp` = the SYNC time and `active_duration_ms` = a DELTA; a **tab switch** (`is_periodic:false, delta_ms:0`) has `timestamp` = the session START (CONSTANT) and `active_duration_ms` = the CUMULATIVE session total. BOTH writers ran `delta_ms || active_duration_ms`, collapsing them, and the app's insert path then unconditionally overwrote its own periodic branch with `Math.min(sessionDuration, 1h)`. So a snapshot re-delivered N times (MV3 service-worker restarts, the extension's retry queue, an evicted in-memory map) appended N rows AT ONE TIMESTAMP, each carrying the whole session again: measured 60 rows at `2026-10-13T16:15:10.675Z` (obsidianui.dev) growing ~30 s per row, 133 of 140 capped rows are `is_browser_tracking=1`, days claiming 139.0 h / 108.1 h. **THE MODEL THAT FIXES IT: session identity = (browser, domain, session-start); a periodic payload ADDS (bounded by the DELTA cap), a tab-switch snapshot may only RAISE (bounded by the SESSION ceiling — a 3 h session must never truncate to a 10-minute delta cap); and THE DATABASE IS THE SESSION REGISTRY, not the in-memory map, because an in-memory map cannot survive a restart. A periodic delta's timestamp is its sync time, so it cannot match the session start exactly — it needs a BOUNDED nearest-row merge window.** `agent/probes/tracking-browser-idempotency.probe.mjs` (14/14) runs the real `ingest()` against a mock table: **1 row / 31.5 min fixed vs 60 rows / 16.8 h pre-fix.** Three corollaries, each measured: (1) **the daemon's `addLog` INSERT had no `browser_name`/`profile_id` columns AT ALL** — that is why 5,835 of 6,345 browser rows are unattributed, and no upstream fix could ever have recorded the browser; (2) **`is_browser_tracking=1 AND domain IS NULL` is 0 rows**, so the dedup branch in `handleBrowserData` is DEAD CODE; (3) **`newSessionDuration` was read at line 23284 but declared at 23303 — a `let` in the temporal dead zone, i.e. a latent ReferenceError, and the same trap appears whenever two branches share a helper and one declares it.** Finally, **the canonical-timeline change is a PAIR, not a line: suppressing the generic browser app row ALSO removes the browser from `daily_stats`/`sessions`/`daily_aggregates`, because `updateAggregates` deliberately excludes website rows — shipping the suppression alone silently deletes the browser's total from those tables.** Website rows are excluded there on purpose (the browser is logged as an app row), so suppressing one requires lifting the other: the invariant "never both" is what makes either correct.

- [2026-10-18] **A `fixed inset-0` ErrorBoundary FALLBACK MUST BE KEYED BY THE STATE THAT CHANGES WHEN YOU NAVIGATE — AND UNDER `HashRouter` THAT CAN NEVER BE `location.pathname`.** `App.tsx:3935` wraps the routes in `<ErrorBoundary key={location.pathname}>` and mounts the `/life` boundary (`App.tsx:3994`) with **no key**.
