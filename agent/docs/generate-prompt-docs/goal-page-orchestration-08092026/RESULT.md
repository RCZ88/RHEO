## 8.3 DB Schema Specification

### 8.3.1 New table: `todos`

```sql
CREATE TABLE IF NOT EXISTS todos (
  id TEXT PRIMARY KEY,
  text TEXT NOT NULL,
  done INTEGER NOT NULL DEFAULT 0,
  -- HIERARCHY EDGE (at most ONE non-null; enforced below):
  goal_id TEXT,            -- parent: goal this todo serves
  schedule_id TEXT,        -- parent: schedule block this todo belongs to
  parent_todo_id TEXT,     -- parent: another todo (subtask)
  -- RELATIONSHIP EDGE (independent of hierarchy):
  deadline_id TEXT,        -- linked deadline row (deadline.goal_id chains upward)
  -- FALLBACK DATE FIELDS (precedence: deadline_id > due_date > deadline_text)
  due_date TEXT,           -- YYYY-MM-DD
  deadline_text TEXT,      -- display annotation when no link/row
  reminder TEXT DEFAULT 'none',
  sort_order INTEGER DEFAULT 0,
  created_at TEXT DEFAULT (datetime('now')),
  completed_at TEXT,
  CHECK (
    (CASE WHEN goal_id IS NOT NULL THEN 1 ELSE 0 END)
  + (CASE WHEN schedule_id IS NOT NULL THEN 1 ELSE 0 END)
  + (CASE WHEN parent_todo_id IS NOT NULL THEN 1 ELSE 0 END)
  <= 1
  )
);
```

Design rationale (binding): the hierarchy parent is a single edge — storing
`child_todo_ids` arrays on parents is forbidden (two stores for one fact).
`deadline_id` is deliberately OUTSIDE the CHECK: a todo may sit in a schedule
block AND be due by a deadline ("a todo in a schedule with a deadline"), while
still having exactly one tree parent. A "habit parent" needs no column — habits
are goals (`is_habit=1`), so `goal_id` covers them.

### 8.3.2 Guarded ALTERs (existing tables)

```sql
-- Pattern: read PRAGMA table_info(<t>) first; add only if column absent.
ALTER TABLE schedule_entries ADD COLUMN goal_id TEXT;   -- BUG FIX: form already collects it
ALTER TABLE deadlines         ADD COLUMN goal_id TEXT;  -- habit link = goal_id → is_habit goal
```

No `habit_id` column anywhere (redundant with goal_id → habit-goal). No foreign
keys (app-level integrity, matching all existing tables); all link rendering must
tolerate dangling IDs.

### 8.3.3 Indexes

```sql
CREATE INDEX IF NOT EXISTS idx_todos_goal     ON todos(goal_id)         WHERE goal_id IS NOT NULL;
CREATE INDEX IF NOT EXISTS idx_todos_parent   ON todos(parent_todo_id)  WHERE parent_todo_id IS NOT NULL;
CREATE INDEX IF NOT EXISTS idx_todos_schedule ON todos(schedule_id)     WHERE schedule_id IS NOT NULL;
CREATE INDEX IF NOT EXISTS idx_todos_deadline ON todos(deadline_id)     WHERE deadline_id IS NOT NULL;
CREATE INDEX IF NOT EXISTS idx_deadlines_goal ON deadlines(goal_id)     WHERE goal_id IS NOT NULL;
CREATE INDEX IF NOT EXISTS idx_schedule_goal  ON schedule_entries(goal_id) WHERE goal_id IS NOT NULL;
```

## 8.4 IPC Specification

Channel style: `todo:*` (matches the newer `notes:*` / `goal:*` families).

| Channel | Payload → Response | Notes |
|---|---|---|
| `todo:list` | `{ from?, to?, goalId? }` → `{ success, todos: HydratedTodo[] }` | LEFT JOINs goals/schedule/deadlines/parent-todo for parent labels + done flags. Dangling parents hydrate as `{ label: null }` |
| `todo:create` | `{ text, goal_id?, schedule_id?, parent_todo_id?, deadline_id?, due_date?, deadline_text?, reminder? }` → `{ success, todo }` | Rejects with `{ success:false, error:'multiple_parents' }` if CHECK would trip. Validates referenced IDs exist (warn-not-fail on dangling) |
| `todo:update` | `{ id, patch }` → `{ success, todo }` | Allowed: text, done, due_date, deadline_text, reminder, sort_order, and link fields. Parent change = single UPDATE that nulls all three then sets the new one (transaction) |
| `todo:toggle` | `{ id, done }` → `{ success }` | Sets/clears `completed_at`. NEVER writes goals.progress_seconds (§8.10) |
| `todo:delete` | `{ id }` → `{ success, orphaned: number }` | `UPDATE todos SET parent_todo_id=NULL WHERE parent_todo_id=?` — orphan, never cascade |
| `todo:get-connections` | `{ entityType, entityId }` → `{ success, graph: ConnectionGraph }` | ≤4 queries, batched (§8.10 N+1 law) |

Modified existing handlers:

| Channel | Change |
|---|---|
| `add-schedule-entry` | Persist `goal_id` (validate the goal exists; store even if dangling with console warn) |
| `update-schedule-entry` | Accept `goal_id` in patch |
| `get-schedule` | Return `goal_id` on entries |
| `add-deadline` / `update-deadline` | Accept + persist `goal_id` |
| `get-deadlines` | Return `goal_id` |

Preload bridges added: `todoList`, `todoCreate`, `todoUpdate`, `todoToggle`,
`todoDelete`, `todoGetConnections`; existing schedule/deadline bridges extended
to pass `goal_id`.

## 8.5 Type Specification

Add to `src/types/goals.ts` (strict, no `any`):

```ts
export interface Todo {
  id: string;
  text: string;
  done: boolean;
  hierarchyParent?: { type: 'goal' | 'schedule' | 'todo'; id: string } | null;
  deadlineId?: string | null;   // relationship edge
  dueDate?: string | null;      // fallback 1
  deadlineText?: string | null; // fallback 2 (display only)
  reminder?: 'none' | 'at_time' | '15min' | '1hour' | '1day';
  sortOrder?: number;
  createdAt: string;
  completedAt?: string | null;
}

export type PlanEntityType = 'todo' | 'goal' | 'ltg' | 'habit' | 'deadline' | 'schedule' | 'note';

export interface PlanEntityRef {
  entityType: PlanEntityType;
  id: string;
  label: string;          // resolved title/text; '(deleted)' when dangling
  missing?: boolean;      // true when the referenced row no longer exists
}

export interface ConnectionGraph {
  entity: PlanEntityRef;
  parent?: PlanEntityRef | null;        // hierarchy parent (todo only)
  children: PlanEntityRef[];            // todos, sub-goals, linked deadlines/schedule (by direction)
  deadline?: PlanEntityRef | null;      // todo → deadline
  linkedGoal?: PlanEntityRef | null;    // deadline/schedule → goal
  notes: PlanEntityRef[];               // notes whose links[] reference this entity
  crossFeatureLink?: CrossFeatureLink | null; // goal.cross_feature_link, now surfaced
}
```

A discriminated union on `entityType` is used by the Explorer; no god-interface.
Helpers live in `src/lib/planGraph.ts`: `getParent`, `getChildren`, `getConnections`
— pure functions over batched arrays, no component-state coupling.

## 8.10 Known Risks & Invariants

- **Bidirectional consistency:** solved by construction — the edge lives only on
  the child; parents are always derived. There is nothing to de-sync.
- **N+1 law:** `todo:get-connections` and tree building resolve in ≤4 queries /
  batched arrays, never per-node queries. Notes lookup uses `LIKE` on
  `notes.links` — acceptable at current note counts; revisit if notes >1k.
- **Dangling refs:** every render path tolerates missing rows (`missing: true`,
  "(deleted)" labels, "Unlinked" badges). A dangling link never throws.
- **Precedence:** deadline display resolves `deadline_id` → `due_date` →
  `deadline_text`, first hit wins; Explorer states which source is shown.
- **No silent writes:** todo toggling never mutates goal progress/rolls streaks
  (invariant; deferred feature listed in §8.11).
- **Deletion:** no cascade deletes, ever. Orphan flow is visible and reversible
  via bulk re-link.
- **Migration:** live-user-DB ALTERs only behind the Phase-1 backup gate.
