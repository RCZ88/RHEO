# The Git Mental Model: Commits Are Snapshots, Branches Are Pointers
@mastery L3

You have been using Git for a while now — `commit`, `push`, `diff`, and `checkout` are in your muscle memory. But `checkout` keeps biting you. It replaces files, destroys uncommitted work, and sometimes it feels like rolling a dice. Here is the truth: the reason `checkout` confuses you is not that it is complicated. It is that `checkout` does *three completely different things* depending on what you pass to it, and without the mental model of what Git actually *is*, you cannot predict which one it will pick.

So before we touch a single branch, let us build the model. Everything else — branching, merging, rebasing, recovering — falls naturally out of this foundation.

## Git stores snapshots, not diffs

Some version control systems (like SVN's delta storage, or the common misconception about Git) store *changes* — "line 3 was changed from X to Y." Git does not work that way. Every commit stores a **complete snapshot** of every file in your project at that moment. If a file did not change between two commits, Git does not duplicate it; it stores a pointer to the previous version. But conceptually, a commit *is* a full picture of your project tree.

This is why `git diff` is fast and why `git checkout` can be dangerous: checking out a commit means "replace my entire working directory with this snapshot." If you have uncommitted changes that conflict, Git either refuses (if they overlap) or silently overwrites them (if you force it).

```bash
# What git actually stores per commit:
# commit <sha> {
#   tree: <sha of the directory structure>
#   parent: <sha of the previous commit>
#   author: name <email> timestamp
#   message: "your commit message"
# }
#
# The tree points to blobs (file contents) and subtrees (directories).
# Unchanged files point to the same blob SHA as the parent commit.
```

## The DAG: commits form a directed acyclic graph

Each commit points to its parent (or parents, for merge commits). This creates a chain — or more precisely, a **directed acyclic graph (DAG)**. The `parent` field is what connects commits into history. A normal commit has one parent. A merge commit has two. The very first commit has none.

```mermaid
graph RL
    C1["C1<br>init"] --> C0["(root)"]
    C2["C2<br>add auth"] --> C1
    C3["C3<br>fix login"] --> C2
    C4["C4<br>add tests"] --> C3
    C5["C5<br>dark mode"] --> C2

    main["main"] --> C4
    feature["feature/dark-mode"] --> C5
    HEAD["HEAD"] --> main

    style main fill:#4A90D9,color:#fff
    style feature fill:#D9534F,color:#fff
    style HEAD fill:#5CB85C,color:#fff
```

Read this diagram carefully. The commits (C1–C5) are the actual history. Everything else — `main`, `feature/dark-mode`, `HEAD` — is just a **label pointing at a commit**. That is the single most important sentence in this entire lesson:

**A branch is not a collection of commits. A branch is a single pointer to one commit.**

When you commit on `main`, Git creates a new commit whose parent is C4, then moves the `main` pointer forward to the new commit. That is it. That is all "committing to a branch" means. The branch label slides forward.

`HEAD` is a special pointer — it points to *the branch you are currently on*. When you run `git commit`, Git reads HEAD to find your current branch, finds that branch's commit, uses it as the parent, creates the new commit, and advances the branch pointer. HEAD → main → C4 is the chain.

## Why this model prevents disasters

When you understand that `main` is just a pointer, several things become obvious:

- **Creating a branch is instant.** Git does not copy any files. It writes a 41-byte file (the commit SHA + newline) at `.git/refs/heads/feature/dark-mode`. That is why branching in Git is nearly free, unlike SVN where branching copies the entire repository.

- **Switching branches changes your working directory.** `git switch feature/dark-mode` means: look at the commit that `feature/dark-mode` points to, and make your working directory match that snapshot. If you have uncommitted changes that conflict with files in that snapshot, Git will refuse — it is protecting you. If the changes do not conflict (different files), Git carries them along.

- **`git checkout <file>` is fundamentally different from `git checkout <branch>`.** Checking out a *branch* swaps your working directory to that branch's snapshot. Checking out a *file* means "throw away my changes to this file and replace it with the committed version." Same command, completely different operation. This is why `git checkout` destroys your work: you thought you were switching branches, but you passed a filename, and Git interpreted it as "discard my changes."

This is also why Git 2.23 introduced `git switch` and `git restore` — to split the overloaded `checkout` into two unambiguous commands. We will use `switch` throughout this lesson.

::: callout warning
The command `git checkout .` (with a dot) means "discard ALL uncommitted changes in the entire working directory." There is no confirmation prompt. There is no undo for uncommitted work. If you have ever felt like Git "just replaced everything," this is almost certainly what happened — you ran a checkout variant that discarded your working directory changes.
:::

## The three areas of Git

Before we move to branching, you need to understand the three areas, because every Git command operates on some combination of them:

```bash
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│  Working Directory │ ──▶ │  Staging Area    │ ──▶ │  Repository (HEAD)│
│  (your files on    │ add │  (index: what    │ commit│  (commits, the   │
│   disk, what you   │ ──▶ │   will be in the │ ──▶ │   DAG we just     │
│   are editing)     │     │   next commit)   │     │   drew)           │
└─────────────────┘     └─────────────────┘     └─────────────────┘
        ▲                                                   │
        │           checkout / switch / restore             │
        └───────────────────────────────────────────────────┘
```

1. **Working directory** — the actual files on your disk. What your editor sees.
2. **Staging area (index)** — the set of changes you have `git add`-ed, ready to be committed.
3. **Repository (HEAD)** — the committed snapshots, the DAG.

- `git add` moves changes from working directory → staging.
- `git commit` moves changes from staging → repository (creates a new commit, advances the branch pointer).
- `git restore` (or legacy `git checkout -- <file>`) moves changes from repository → working directory, discarding your local edits.
- `git reset` can move the branch pointer backward and optionally update staging and working directory to match.

When you understand these three areas and how commands shuffle data between them, you can predict what any Git command will do without running it. That is the meta-skill.

# Branching: Why and How to Separate Your Work
@mastery L3
@prereq the-git-mental-model-commits-are-snapshots-branches-are-pointers

Now that you know a branch is just a pointer, the question becomes: why bother moving that pointer around? Why not just commit everything to `main`?

You already suspect the answer — you said it yourself: "that's not a good practice." But let us make the reasoning precise, because understanding *why* will make the workflow feel natural rather than like a rule you are following on faith.

## Why separate work into branches

**1. `main` should always be deployable.** If you commit a half-finished feature to `main` and then need to fix an urgent bug, you have a problem: your bug fix commit sits on top of broken code. You cannot deploy `main` without deploying the half-finished feature. With branches, you can hotfix `main` directly, deploy it, and your feature work sits untouched on its own branch.

**2. Isolation enables experimentation.** Want to try a refactor? Create a branch. If it goes wrong, you delete the branch — one command, no harm done. If you had done it on `main`, you would need to carefully revert individual commits, hoping you do not miss something.

**3. Review and collaboration.** When you push a branch, you can open a Pull Request (PR). A PR is a conversation: "here is what I changed, here is why, please review before it goes into `main`." You cannot do this if everything goes straight to `main`. The branch boundary is what makes review possible.

**4. Parallel work streams.** You are working on a feature. You suddenly need to context-switch to a bug. With branches: commit your feature work (even if incomplete), switch to `main`, create a `hotfix/bug-xyz` branch, fix it, merge it, switch back to your feature branch. Everything is clean. Without branches, you are stashing changes manually or copying files around.

## The branching workflow, step by step

Here is the workflow you should internalize. Every feature, every bugfix, every experiment follows this pattern:

```bash
# 1. Make sure you are on main and it is up to date
git switch main
git pull origin main

# 2. Create a new branch for your work
git switch -c feature/user-auth

# 3. Work, stage, commit — repeat as needed
git add src/auth.py
git commit -m "add login endpoint"

git add src/models.py
git commit -m "add User model with password hashing"

# 4. Push the branch to the remote (sets up tracking with -u)
git push -u origin feature/user-auth

# 5. Open a Pull Request on GitHub/GitLab (via the web UI)

# 6. After the PR is merged, clean up
git switch main
git pull origin main          # get the merged changes
git branch -d feature/user-auth  # delete local branch (safe — refuses if unmerged)
git push origin --delete feature/user-auth  # delete remote branch
```

Read that workflow a few times. Notice the symmetry: you start from a clean `main`, you create a branch, you do your work, you merge it back, you clean up. The branch is born from `main` and returns to `main`. Nothing else gets polluted.

::: callout tip
The `-c` flag in `git switch -c feature/user-auth` means "create and switch in one step." It is equivalent to `git branch feature/user-auth` followed by `git switch feature/user-auth`, but nobody types both commands. Always use `-c`.
:::

## Branch naming conventions

Names matter. A branch called `stuff` or `test2` tells you nothing three weeks later. Use a convention:

| Prefix | Purpose | Example |
|---|---|---|
| `feature/` | New functionality | `feature/user-auth` |
| `fix/` or `bugfix/` | Bug fixes | `fix/login-redirect-loop` |
| `hotfix/` | Urgent production fix | `hotfix/sql-injection` |
| `refactor/` | Code restructuring, no behavior change | `refactor/extract-auth-module` |
| `experiment/` or `spike/` | Throwaway exploration | `spike/websocket-vs-sse` |
| `docs/` | Documentation only | `docs/api-reference` |

The slash creates a visual hierarchy in most Git UIs — GitHub and GitLab will group `feature/*` branches together. It is a minor thing that pays off when you have twenty branches.

## `git switch` vs `git checkout` — the definitive guide

Git 2.23 (August 2019) split the overloaded `checkout` into two commands. Here is the mapping:

```bash
# OLD (checkout does everything)              # NEW (split into switch + restore)
git checkout feature/auth                  →  git switch feature/auth
git checkout -b feature/auth               →  git switch -c feature/auth
git checkout -                             →  git switch -           # go back to previous branch
git checkout -- .                          →  git restore .           # discard working dir changes
git checkout HEAD -- file.py               →  git restore --source=HEAD file.py
git checkout <commit> -- file.py           →  git restore --source=<commit> file.py
```

The key insight: `switch` only ever changes which branch/commit your working directory is based on. It never discards individual file changes. `restore` only ever replaces file contents. It never switches branches. The ambiguity that destroyed your project is gone.

```bash
# These are now unambiguous:
git switch feature/auth     # "I want to work on this branch" — refuses if uncommitted changes conflict
git restore src/app.py      # "I want to throw away my changes to this file" — no branch switching involved
```

::: callout warning
`git switch` will refuse to switch if you have uncommitted changes that conflict with the target branch. This is the safety net that `git checkout` did not reliably provide. If you see "error: Your local changes to the following files would be overwritten by checkout," that is Git protecting you. Do not use `--force` to bypass it unless you are certain you want to lose those changes.
:::

## Working with remote branches

When you clone a repository, you get the `main` branch and a remote called `origin`. But `origin` has other branches too. Here is how to interact with them:

```bash
# See all branches (local and remote)
git branch -a

# Output looks like:
#   feature/auth
#   main
#   remotes/origin/feature/auth
#   remotes/origin/main
#   remotes/origin/feature/dark-mode

# Create a local branch that tracks a remote branch
git switch feature/dark-mode
# Git automatically creates a local branch tracking origin/feature/dark-mode

# Fetch all remote branch updates without merging
git fetch --all

# Delete a remote branch (after it has been merged)
git push origin --delete feature/dark-mode
```

The `remotes/origin/...` branches are **remote-tracking branches**. They are Git's record of where each branch was on the remote the last time you fetched. They are read-only — you cannot commit to them. They update only when you `git fetch` or `git pull`. This is why `git status` says "your branch is behind origin/main by 3 commits" — it is comparing your local `main` pointer to the `origin/main` pointer, which was set during your last fetch.

## What happens when you switch branches with uncommitted changes

This is the scenario that used to bite you. Let us trace it precisely:

```bash
# You are on main, editing src/app.py
git switch -c feature/new-api
# If src/app.py has no conflicts with the feature branch's version → changes carry over silently
# If src/app.py was also modified on the feature branch → Git refuses, protects your changes

# If Git refuses, you have three options:
git stash              # temporarily save changes, clean working directory
git switch feature/new-api  # now it works
git stash pop          # restore your changes on the new branch

# OR: commit your changes first (even a WIP commit)
git add -A && git commit -m "WIP: partial app.py changes"
git switch feature/new-api

# OR: discard your changes (if you do not want them)
git restore src/app.py
git switch feature/new-api
```

The key insight: **Git refuses to switch when it would overwrite uncommitted changes.** This is a feature, not a bug. The old `git checkout` was less reliable about this, which is why `git switch` exists.

# Merging and Rebasing: Combining Branches Without Chaos
@mastery L3
@prereq branching-why-and-how-to-separate-your-work

You have a feature branch with three commits. `main` has moved forward with two more commits since you branched off. Now you want to combine them. You have two options: **merge** or **rebase**. Understanding the difference — and when to use each — is what separates someone who uses Git from someone who understands Git.

## The merge: fast-forward vs three-way

When you run `git merge feature/auth` while on `main`, Git checks: has `main` moved since `feature/auth` diverged?

**Fast-forward merge** — if `main` has NOT moved, Git simply slides the `main` pointer forward to point at the same commit as `feature/auth`. No new commit is created. The history is perfectly linear:

```mermaid
graph LR
    subgraph "Before merge"
        A1["A"] --> B1["B"]
        B1 --> C1["C"]
        B1 --> D1["D"]
        D1 --> E1["E"]
        M1["main"] --> C1
        F1["feature"] --> E1
    end
    subgraph "After fast-forward"
        A2["A"] --> B2["B"]
        B2 --> D2["D"]
        D2 --> E2["E"]
        M2["main"] --> E2
        F2["feature"] --> E2
    end
```

**Three-way merge** — if `main` HAS moved, Git must combine both histories. It finds the common ancestor (the commit where the branches diverged), computes the changes on each side, and creates a new **merge commit** with two parents:

```mermaid
graph LR
    A["A<br>common ancestor"] --> B["B"]
    B --> C["C<br>main moved"]
    B --> D["D"]
    D --> E["E<br>feature work"]
    C --> M["M<br>merge commit"]
    E --> M
    M2["main"] --> M
    style M fill:#5CB85C,color:#fff
    style M2 fill:#4A90D9,color:#fff
```

The merge commit M has two parents: C (from `main`) and E (from `feature`). This preserves the full history — you can see exactly when and how the branches diverged and merged.

```bash
# Fast-forward merge (main hasn't moved)
git switch main
git merge feature/auth
# Output: "Updating abc1234..def5678. Fast-forward."
# No merge commit created. History is linear.

# Three-way merge (main has moved)
git switch main
git merge feature/auth
# Output: "Merge made by the 'ort' strategy."
# A merge commit is created with two parents.
```

## The rebase: replaying your commits

Rebase does something fundamentally different. Instead of creating a merge commit, it **replays your feature branch's commits on top of the latest `main`**, as if you had started your feature branch from the current `main` instead of the old one.

```mermaid
graph LR
    subgraph "Before rebase"
        A1["A"] --> B1["B"]
        B1 --> C1["C<br>main"]
        B1 --> D1["D"]
        D1 --> E1["E<br>feature"]
    end
    subgraph "After rebase feature onto main"
        A2["A"] --> B2["B"]
        B2 --> C2["C<br>main"]
        C2 --> D2["D'<br>replayed"]
        D2 --> E2["E'<br>replayed"]
        F2["feature"] --> E2
    end
    style D2 fill:#D9534F,color:#fff
    style E2 fill:#D9534F,color:#fff
```

Notice: D and E become D' and E'. They have **different SHA hashes** because they have different parents (C instead of B). The original D and E still exist in Git's object database (recoverable via reflog), but they are no longer part of any branch. The feature branch now looks like it was always based on the latest `main`.

```bash
# Rebase your feature branch onto the latest main
git switch feature/auth
git fetch origin
git rebase origin/main

# Then switch to main and fast-forward merge (no merge commit needed!)
git switch main
git merge feature/auth   # This is now a fast-forward because rebase replayed on top of main
```

The result is a perfectly linear history. No merge commit. No "merge branch X into main" noise.

## Merge vs rebase: when to use each

This is one of the most debated topics in Git, but the decision tree is actually simple:

| Criterion | Merge | Rebase |
|---|---|---|
| Preserves exact history | Yes — every commit timestamp and order is preserved | No — replayed commits get new SHAs and timestamps |
| Creates extra merge commits | Yes, for three-way merges | No — linear history |
| History readability | Can be noisy with merge commits | Clean and linear |
| Safe for shared branches | Yes — never rewrites history | No — rewrites commits, breaks collaborators |
| Conflict resolution | All at once, in one merge | One commit at a time, during rebase |

**The golden rule of rebase:** Never rebase commits that have been pushed to a remote and might be pulled by someone else. Rebase rewrites history. If someone else has based work on your original commits, and you rewrite those commits, their history diverges from yours in a way that is extremely painful to fix.

```bash
# SAFE: rebase a local feature branch before pushing (nobody else has it)
git switch feature/auth
git rebase main
git push -u origin feature/auth

# DANGEROUS: rebase a branch that others have already pulled
git switch main
git rebase origin/main   # DO NOT DO THIS if others share main
git push --force         # This force-push overwrites remote history
# Anyone who pulled the old main now has a broken local repository
```

::: callout caution
`git push --force` is the command that makes rebase dangerous on shared branches. It overwrites the remote branch with your local version, discarding any commits that were on the remote but not on your local. If a teammate pushed commits that you did not have, those commits are gone from the remote. Use `--force-with-lease` instead, which refuses to push if the remote has been updated since your last fetch — it is a safety net that prevents the most common accident.
:::

## Conflict resolution: the part that scares everyone

Merge conflicts happen when both branches changed the same lines of the same file, and Git cannot automatically determine which version to keep. Here is exactly what happens, step by step:

```bash
git switch main
git merge feature/auth
# Output:
# Auto-merging src/app.py
# CONFLICT (content): Merge conflict in src/app.py
# Automatic merge failed; fix conflicts and then commit the result.
```

Git pauses the merge. Your working directory now contains conflict markers in the affected files:

```python
# src/app.py — what it looks like during a conflict

def get_user(user_id):
<<<<<<< HEAD
    # Main branch version: use the new ORM
    return db.session.query(User).filter_by(id=user_id).first()
=======
    # Feature branch version: use raw SQL
    cursor.execute("SELECT * FROM users WHERE id = ?", (user_id,))
    return cursor.fetchone()
>>>>>>> feature/auth
```

- `<<<<<<< HEAD` — your current branch (`main`) version
- `=======` — the separator
- `>>>>>>> feature/auth` — the incoming branch version

**Your job:** edit the file to what the correct merged result should be. Delete the markers. Keep one version, keep the other, or write a combination:

```python
# Resolved version — I decided to use the ORM approach but add the error handling from the feature branch

def get_user(user_id):
    user = db.session.query(User).filter_by(id=user_id).first()
    if user is None:
        raise NotFoundError(f"User {user_id} not found")
    return user
```

Then:

```bash
git add src/app.py              # mark the file as resolved
git merge --continue            # finish the merge (creates the merge commit)
# OR, if you want to bail out:
git merge --abort               # undo everything, back to pre-merge state
```

::: callout tip
During a rebase, conflicts are resolved one commit at a time. After fixing conflicts for a single commit, you run `git rebase --continue` to move to the next one. If a commit becomes empty after rebase (its changes were already applied on main), Git will ask if you want to skip it — run `git rebase --skip`. And as with merge, `git rebase --abort` cancels the whole thing and puts you back where you started.
:::

## A realistic merge walkthrough

Let us trace through a complete scenario — the kind you will actually face:

```bash
# You started a feature branch a week ago
git switch -c feature/payment-integration

# You made 4 commits over the week
# Meanwhile, your teammate merged 3 commits into main

# Time to merge. First, update your local main
git switch main
git pull origin main

# Option A: Merge (safe, preserves history)
git switch feature/payment-integration
git merge main
# If conflicts: resolve them, git add, git merge --continue
git switch main
git merge feature/payment-integration   # fast-forward or merge commit
git push origin main

# Option B: Rebase (cleaner history, resolve conflicts per-commit)
git switch feature/payment-integration
git rebase main
# If conflicts per commit: resolve, git add, git rebase --continue
# If a commit is now empty: git rebase --skip
git switch main
git merge feature/payment-integration   # always fast-forward now
git push origin main

# Clean up
git branch -d feature/payment-integration
git push origin --delete feature/payment-integration
```

Notice that both options end the same way: the feature is on `main`, the branch is deleted. The difference is entirely in the shape of the commit history.

::: layer L4 deeper
## Interactive rebase: rewriting history before it goes public

Interactive rebase (`git rebase -i`) is the tool for polishing your commit history before pushing. It lets you reorder, combine, edit, or drop commits on a local branch.

```bash
# Rebase the last 5 commits interactively
git rebase -i HEAD~5
```

This opens your editor with a list of commits:

```text
pick abc1234 add payment model
pick def5678 WIP: debugging stripe webhook
pick ghi9012 fix typo in model
pick jkl3456 add payment endpoint
pick mno7890 add tests for payment

# Commands:
# p, pick   = use commit
# r, reword = use commit, but edit the commit message
# e, edit   = use commit, but stop for amending
# s, squash = use commit, but meld into previous commit
# f, fixup  = like "squash", but discard this commit's message
# x, exec   = run command using shell
# d, drop   = remove commit
```

You might rewrite this as:

```text
pick abc1234 add payment model
fixup def5678 WIP: debugging stripe webhook    # squash into previous, discard message
fixup ghi9012 fix typo in model                # squash into previous, discard message
reword jkl3456 add payment endpoint            # keep, but edit the message
pick mno7890 add tests for payment
```

Result: 5 messy commits become 3 clean ones. The WIP and typo commits are absorbed into the model commit as if they never existed separately. This is exactly the kind of cleanup you do *before* pushing — never after.

The golden rule still applies: only rebase commits that have not been pushed to a shared remote. Once a commit is on `origin`, assume someone else has it.
:::

## `git revert` vs `git reset` — the critical distinction

This trips up everyone. The difference is simple but consequential:

- **`git reset`** moves the branch pointer *backward*, as if the later commits never happened. It **rewrites history**. The "undone" commits disappear from the branch. This is fine for local branches, but destructive on shared branches.

- **`git revert`** creates a *new commit* that undoes the changes of a previous commit. It **preserves history** — the original commit stays, and a new "undo" commit is added on top. This is safe for shared branches because it does not rewrite anything.

```bash
# You committed a bug to main and pushed it. Two more commits came after.
# History: A → B(bug) → C → D

# WRONG: git reset --hard B  (rewrites history, breaks anyone who pulled C and D)
# RIGHT: git revert B        (creates a new commit E that undoes B's changes)
# Result: A → B(bug) → C → D → E(undoes B)
```

```bash
# You committed locally but haven't pushed. Nobody else has these commits.
# History (local only): A → B(typo) → C

# FINE: git reset --hard B  (removes C, which nobody else has)
# OR:   git revert C        (also works, but adds a revert commit unnecessarily)
# OR:   git reset --soft B  (removes C but keeps the changes staged — safest)
```

The mental model: `reset` is for undoing things that only you have. `revert` is for undoing things that others might have.

## `git stash` — the parking lot

You are halfway through a change when you need to switch branches. You do not want to commit incomplete work (messy history), but you cannot switch because of uncommitted changes. Enter `git stash`:

```bash
# Park your current changes (working directory + staging area)
git stash
# Working directory is now clean — matches the last commit

# Do whatever you need: switch branches, fix a bug, etc.
git switch main
git switch -c hotfix/urgent-bug
# ... fix, commit, merge ...

# Come back and restore your changes
git switch feature/original-work
git stash pop
# Your changes are back, and the stash is removed from the stash list

# Other stash operations:
git stash list          # see all stashes (you can have multiple)
git stash show -p       # see what's in the most recent stash (patch format)
git stash drop          # delete the most recent stash without applying it
git stash clear         # delete ALL stashes (dangerous — no confirmation)
```

::: callout tip
`git stash pop` applies the stash AND removes it from the stash list. If there are conflicts when applying, Git leaves the stash in the list so you can try again or drop it manually. `git stash apply` applies the stash but keeps it in the list — useful if you want to apply the same stash to multiple branches.
:::

## `git reflog` — the safety net you did not know existed

Here is the most reassuring fact in all of Git: **almost nothing is truly gone.** When you `git reset --hard`, delete a branch, or even do a bad rebase, the commits are not deleted — they are just unreachable from any branch. Git keeps them for approximately 90 days (configurable via `gc.reflogExpire`).

The `reflog` (reference log) records every time HEAD or any branch pointer moves. It is your personal undo history:

```bash
git reflog
# Output (most recent first):
# a1b2c3d HEAD@{0}: reset: moving to HEAD~1
# e4f5g6h HEAD@{1}: commit: add payment endpoint
# i7j8k9l HEAD@{2}: commit: add payment model
# m0n1o2p HEAD@{3}: checkout: moving from main to feature/payment
# q3r4s5t HEAD@{4}: pull origin main
```

Each line shows where HEAD was at that moment. Even after a `reset --hard`, the "lost" commits are still there — you just need to find their SHA and reset back:

```bash
# You accidentally ran: git reset --hard HEAD~2
# Two commits "disappeared"

git reflog
# Find the SHA where HEAD was BEFORE the reset (e.g., e4f5g6h)

git reset --hard e4f5g6h
# Your commits are back. The reflog remembered them.
```

```bash
# You accidentally deleted a branch
git branch -D feature/important-work

git reflog
# Find the last commit SHA that feature/important-work pointed to

git branch feature/important-work <sha>
# Branch restored, pointing at the right commit
```

::: callout warning
The reflog only records *committed* state. Uncommitted changes (working directory edits that were never staged or committed) are NOT in the reflog. If you run `git restore .` or `git checkout .` and discard uncommitted work, the reflog cannot help you. For uncommitted staged changes, `git fsck --lost-found` can sometimes recover dangling blobs, but it is unreliable. The lesson: **commit early, commit often.** You can always amend or rebase later. Uncommitted work has no safety net.
:::

## `git restore` — the safe file recovery tool

`git restore` is the modern replacement for the file-destruction half of `git checkout`. It is explicit about what it does:

```bash
# Discard uncommitted changes to a file (restore from HEAD)
git restore src/app.py
# This throws away your working directory changes to app.py.
# The committed version replaces your edits. No confirmation. No undo.
# BUT: it only touches the file you specify — it does NOT switch branches.

# Restore a file from a specific commit (not HEAD)
git restore --source=HEAD~2 src/app.py

# Unstage a file (move from staging area back to working directory)
git restore --staged src/app.py
# The file's changes are still in your working directory, just no longer staged.

# Combine: unstage AND discard changes
git restore --staged --worktree src/app.py
# Now the file matches HEAD exactly — all changes gone.
```

The key difference from `git checkout`: `restore` is explicit. `restore src/app.py` always means "replace this file's content." It never means "switch to a branch called src/app.py." The ambiguity is gone.

## A recovery playbook

Here are the scenarios you will actually face, and the exact commands to fix them:

**Scenario 1: "I committed to the wrong branch"**
```bash
# You committed to main but meant to commit to feature/auth
git switch feature/auth        # switch to the correct branch (carries the commit with you if no conflicts)
# If Git refuses due to conflicts:
git stash                      # stash the commit's changes... wait, it's already committed
# Actually for committed work:
git switch feature/auth
git cherry-pick main           # copy the commit from main to feature/auth
git switch main
git reset --hard HEAD~1        # remove it from main (safe if not pushed)
# If already pushed to main: git revert <commit-sha> instead of reset
```

**Scenario 2: "I ran git reset --hard and lost commits"**
```bash
git reflog                     # find the SHA before the reset
git reset --hard <sha>         # restore to that point
```

**Scenario 3: "I deleted a branch I still needed"**
```bash
git reflog                     # find the SHA the branch pointed to
git branch <branch-name> <sha> # recreate the branch at that commit
```

**Scenario 4: "I started a rebase and everything is broken"**
```bash
git rebase --abort             # cancels the rebase, returns to pre-rebase state
# If you already finished the rebase but want to undo:
git reflog                     # find the SHA before the rebase
git reset --hard <sha>
```

**Scenario 5: "I accidentally force-pushed and overwrote someone's commits"**
```bash
# This is the hard one. The remote's reflog is not accessible to you.
# The teammate whose commits were overwritten still has them locally.
# They need to: git push --force-with-lease origin their-branch
# Going forward: ALWAYS use --force-with-lease instead of --force
```

know: git reset --hard is the only reset mode that destroys uncommitted working directory changes; --soft and --mixed preserve working directory contents [progit]
know: git revert creates a new commit that undoes a previous commit's changes, preserving history; git reset rewrites history by moving the branch pointer backward [progit]
know: The reflog records every HEAD and branch pointer movement, making "lost" commits recoverable for approximately 90 days even after operations like reset --hard or branch deletion [gitdocs]
know: git stash temporarily shelves uncommitted changes (both staged and unstaged) and restores a clean working directory; git stash pop applies and removes the stash [gitdocs]
know: Uncommitted working directory changes that were never staged or committed are not recorded in the reflog and are generally unrecoverable if discarded [progit]
misconception: git reset --hard permanently deletes commits | Commits are still in Git's object database for ~90 days and recoverable via reflog; only uncommitted working directory changes are truly lost
misconception: git revert and git reset do the same thing | revert adds a new undo commit preserving history (safe for shared branches); reset rewrites history (safe only for local, unpushed work)
excludes: Git internals (object storage, packfiles, gc);custom reflog configuration;bisect and cherry-pick as recovery tools;submodule recovery
source: progit | Pro Git Book by Scott Chacon and Ben Straub | https://git-scm.com/book/en/v2
source: gitdocs | Git Reference Documentation | https://git-scm.com/docs
:::
